The game. Two opponents command visible armies on a compact, elevated battlefield. Their connected territory generates Minor Arcana that can supply movement, pay for magic or become a Card ability. Member placement determines contact and protection. A fixed Capital and a designated Commander provide clear objectives; attributed Cards, creations and match history connect play to the wider Hapa ecosystem.

Later commercial, hidden-information and permanent-progression policies do not block this work.

1 Game and product goals
Hapa Versus is a two-player tactical card game played on a small battlefield. Each player commands groups of individual fighters, advances them through colored territory, and spends the cards that territory produces on movement or special abilities. The player wins by moving a formation's center into the enemy Capital or killing the enemy Commander. Human players and automated agents may occupy either seat. The same rules and visibility apply to both.
The visual style is 2.5D pixel art. The world has real height, movement and contact positions, while the camera and pixel rendering make it look like a readable tactical board. A territory is a large square on that board. Each territory contains a visible three-by-three arrangement of smaller member slots. A fighter's position within those slots matters: a shield at the front does not automatically protect against arrows arriving from above, and a casualty can open a gap into the formation.
The game combines two kinds of planning. The player chooses a collection of reusable Card and ability definitions before play, then decides how to use the resource cards created during the match. Territory supplies both logistics and magic. Advancing produces different opportunities, while enemy infiltration can interrupt a column's future production. This connection gives players a reason to understand their Cards through repeated use, experiment with combinations, and exchange creations with opponents.
The Hapa purpose
Hapa is the wider project in which identities, media, knowledge, abilities and experiences become attributable, reusable digital records called Hapa Cards. A Hapa Card can describe a character, skill, item, place or other concept. It can have several presentations and uses. For this game, a playable definition gives one such concept precise game behavior. The same source Card may later have a different use in another Hapa application.
The game should make those records useful and desirable through enjoyable play, personal expression, discovery and enduring history. Players should see who created a Card, understand what it does, and be able to build on encountered ideas. Mining, crafting, unit statistics and collection history create further reasons to return. Which benefits carry into later matches remains a format setting that can change as the team learns. This specification makes the records and adjustable policies usable now; it does not prescribe a marketplace, an educational curriculum or a final progression economy.
What the first implementation must achieve
Build a visible, inspectable game that can run a complete match locally and between two independent computers. Both computers must calculate the same result from the same accepted choices. The first implementation includes public Cards, public board state and public submitted orders. Cryptographic trap cards and other hidden effects belong to a later product iteration and are not dependencies for this work. Document version 3.0 is the name of this specification; it does not mean those later gameplay features are now required.
The platform must support the requested board, damage and economy experiments through data and replaceable policies. It must also support new Cards whose written behavior changes an ordinary rule. A card author should be able to grant extra movement, protect a particular face, change a resource contribution, bind a bonus to a mount, or affect an entire column without rewriting unrelated systems. When an idea requires a genuinely new operation, that operation can be added to a versioned rules module with examples that both peers can execute.
Visual explanation is a gameplay requirement. The player must be able to inspect the nine local slots, follow a formation while other columns are active, see which side an attack comes from, and understand why a card or member contributed to the result. The implementation should prioritize that visibility alongside correct simulation.
How to use this specification
This document contains the current game description, the reason for each major system, concrete examples, implementation contracts and a runnable initial configuration. It is intended to be handed to a developer or coding agent without any conversation history. References at the end provide evidence and provenance; reading earlier Hapa Versus documents is not required to implement the behavior described here.
There are three kinds of instruction. A product rule states the requested behavior, such as public hand slots or one current destination. A configurable capability states an alternative the software must support, such as attacker-chosen versus defender-chosen casualties. A starting test setting supplies a concrete value where development needs one, such as a temporary Commander health value. Starting test settings are engineering fixtures for reproducible playtests. They are not claims that CJ has approved final balance, and changing one must not require a new architecture.
A Match Profile is a saved version of those settings together with the board, content and rules versions. Both players agree to that profile before the match. It stays fixed for that match except for changes made by legal in-game effects. A later experiment creates another profile revision. This gives the team freedom to iterate while keeping results understandable and replayable.
Design influences in ordinary language
The reference games provide useful ideas, but familiarity with them is unnecessary. The concentrated fighting associated with League of Legends ARAM suggests readable combat roles and pressure. Chess supplies recognizable movement shapes for mounts. Go suggests the importance of connected position and cutting an opponent's access. Magic the Gathering supplies a model in which individual Cards operate within a shared timing and interaction framework. The rules below define Hapa's own behavior explicitly; a developer must not fill an unspecified detail by importing another game's rules.
The development approach is successive friends-and-family experiments. Keep the system capable of recording what actually happened, then use human feedback and automated matches to compare alternatives. Automated play is a supported way to produce fair, useful competition under the chosen protocol. Reports identify which agents, decks and settings participated so the evidence can be interpreted accurately.
2 Concepts and a complete match walkthrough
The objects a player sees
Two players sit at opposite ends of a battlefield with nine columns. A column runs from one home edge toward the other; a row runs sideways across it. A territory is one playable square where a party can stand. The field has nine, ten or eleven rows depending on the selected board experiment.
A party is a collection of fighters that normally travels together. A member is one fighter inside it. The phrase unit in the original design can refer to either; implementation and UI text must say party or member when that distinction matters. A party has a center position used to determine which territory and column it occupies. This center position exists even when the center slot contains no fighter.
A mount is the center leader that lets a party move and supplies its movement shape. Mount names such as Castle, Bishop and Knight describe travel patterns rather than requiring a literal horse or building. A retainer is a member arranged around that center. A starting Pawn party has five members and an empty center slot. It defends its position but has no ordinary party movement until a mount joins it. When a mount party enters a friendly Pawn party, they merge and retain their members and remaining resources.
The Commander is the special center leader that begins in the middle column on the home row. Its starting territory is the Capital. That territory remains the Capital after the Commander moves. Losing the Commander or allowing an enemy center into the Capital loses the match under the standard victory rules. An ordinary King mount is a movement archetype; it is not automatically the Commander, and this game does not use chess check or checkmate.
The Cards and resources
A Minor Arcana is a generated match card with a suit, a printed number, a Supply value, a colored Mana payload and an optional attached ability. Minting means creating this match instance through game rules. It does not imply a blockchain transaction or a scarce saleable asset. The suits are Wands, Pentacles, Cups and Swords, plus the center lane's wildcard behavior. A suit and a Mana color are different properties: a Wands card can contain Red and Green Mana together.
Supply pays movement distance. Applying a Minor Arcana for Supply consumes that entire card instance and credits one party's movement allowance. Speed says how quickly that party uses distance over simulation time. A party with Speed 2 travels twice as far in one Tick as a Speed-1 party with the same movement permissions, but still spends Supply for the distance traveled.
Mana pays an ability's colored cost. Burning a Minor Arcana consumes the instance and puts its colored quantities into the player's temporary pool. The pool is a set of balances, one for each color. For example, three Red and one Green remain separate quantities. A payment removes the matching amounts. Rainbow may pay an ordinary color requirement, while an explicitly Rainbow-only requirement needs Rainbow. Unspent ordinary pool Mana is cleared at the Tick boundary unless an effect preserves it.
The player can instead use the ability attached to a Minor Arcana. A Spell is a declared magical effect with a cost and timing rule. A Skill is another declared action, often logistical or martial; its Card specifies its own resource cost. Playing an attached ability gives up the same instance's ordinary Supply and Mana uses. Any additional payment comes from other resources. The reusable Card definition remains in the collection after the generated instance is spent.
A player's hand bank is a public row of nine Minor Arcana slots behind the Major Arcana row, one slot for each column. A new card from a column replaces an unspent card still in that column's slot. A Major Arcana is a persistent Card placed in a column reserve. A row Enchantment is a persistent effect placed beside a row. Their location explains where they sit; their individual Card text says whether they affect a region, a particular mount, or both.
The time vocabulary
A Tick, also called a Count, is one logical interval in the game. It is not one animation frame and need not equal a fixed number of wall-clock seconds. At its start, the active columns generate resource cards from the completed board state. Players then make the permitted choices, and the rules advance movement and combat by one interval. The display can play the interval slowly, quickly or one step at a time without changing its result.
The active columns sweep inward and outward. Only parties in the highlighted columns normally receive new movement or ordinary ability orders. Existing orders and battles continue elsewhere. Supply can be delivered to any friendly party in any state, including one that is moving or fighting. A Round runs from one center-column activation to just before the next. The first four Ticks form a prologue; Round 1 is Ticks 5 through 13.
A complete opening explained step by step
Use the starting ten-row test board. Each player has nine mount parties on the home row and nine five-member Pawn parties on the next row. The outer mounts are Castles. Neither player begins with a generated Minor Arcana in the public hand bank. The starting resource curve counts the eligible frontline's row number from home to determine Supply, while deployment rows contribute no colored Mana. Here, the frontline is the furthest qualifying friendly party before the first enemy blocker in that column. The opening therefore emphasizes moving and joining forces before paying for magical effects.
Tick 1 highlights columns 1 and 9. Each player's frontline in either column is the Pawn party on the second home-relative row. The starting resource curve therefore creates a rank-2 Wands card with two Supply and zero Mana in each of the two corresponding hand slots. Both opponents can inspect those cards. A later card from the same column would replace its slot's previous occupant if the player had not used it.
Player A attaches the column-1 card to the column-1 Castle and orders that Castle to the Pawn territory directly ahead. The card leaves the hand slot. The Castle now has two Supply. During the movement interval it crosses one territory step, spends one Supply, and merges with the five-member Pawn party. If the Castle carried three retainers, the combined formation has nine members: the mount, three retainers and five former Pawn members. One Supply remains. The column-9 Castle can do the same, and Player B can perform the mirrored actions.
Tick 2 highlights columns 2 and 8. A Castle with a continuing destination farther ahead can keep moving even though its column is no longer highlighted. A new destination order for it normally waits for an eligible activation, while a Supply delivery can occur now. If the player originally chose only the Pawn territory as its destination, it stops there because that destination has been reached. Merging does not silently invent another destination.
As formations enter configured Mana rows, later activations of those columns produce cards with colored Mana as well as Supply. A player can burn one card to pay another card's Spell cost, spend a card to move farther, or preserve the attached ability for use before its slot is replaced. This is the central tradeoff. A single instance cannot be burned and then attached, or supply its own casting cost after it has already been consumed by that burn.
Suppose two parties eventually meet head-on. The three front Swordsmen on one side contact the opposing three. In the individual-defense example, each Swordsman makes a three-point Physical hit against one point of front Defense, so each receives two damage from its counterpart. Rear Archers can send separate one-point hits from Above; front-facing shields do not protect that face. The selected damage profile determines whether the attacker, defender or an aggregate-party-health rule determines the resulting casualties.
After the fight, survivors can continue toward their saved destinations when the path clears. A retreating party loses its own members that are touching enemies at the instant it retreats. The match ends when an enemy center enters a Capital or a Commander is killed, with a draw if the selected simultaneous event gives both players a loss. The match history records movement, Cards, damage, casualties, mined materials, created items and the result. It can be replayed, compared with another profile, or inspected to explain a surprising outcome.

3 Board layouts and public card reserves

Figure 1 The ten-row starting board and its public banks. Each territory has nine local member positions. The Major Arcana and Minor Arcana banks each have nine slots per player; the side Enchantment bank has one slot per playable row. This conceptual diagram omits the physical contact-strip spacing used by movement.

What the board represents
The battlefield is a grid on which two players move opposing armies. A large playable square is called a territory. A party is a group of characters that travels and fights together. Each territory contains a smaller three-by-three arrangement of member positions, so a player can see both where a party is on the battlefield and where its individual members stand within the formation. Movement across the large grid changes access to resources; the arrangement inside a territory determines which members meet an attack.
A mounted party has a central character, called its Mount, that supplies its movement pattern. Castle, Knight, Bishop, King and Queen are Mount types. The Commander is the particular central character whose death can end the match. The Commander's starting territory is its player's Capital. A player wins the basic format by killing the opposing Commander or moving one of their own party centers into the opposing Capital. The Capital stays at its starting location when its Commander moves. Other card-defined victory conditions can be added to other formats.
Advancing threatens the opposing army and Capital and can increase a column's income. An enemy that gets between a party and its home edge can cut off that advance. The board therefore represents both a battlefield and a logistical route home.
Rows columns and the two viewpoints
A column runs from one player's home edge toward the other player's home edge. A row runs across the battlefield. The playable columns are C1 through C9. Rows are R1 through RN, where N is the number of playable rows in the chosen layout. These shared coordinates always describe the same physical territory on both computers.
Player A starts at the low-numbered end and advances toward increasing row numbers. Player B starts at the high-numbered end and advances toward decreasing numbers. A's Capital is global R1C5; B's is global RNC5. When B views the battlefield from its own home edge, its local column is 10 minus the global column, and its local row is N plus 1 minus the global row. For example, global R10C9 on a ten-row field is B's local R1C1. Camera rotation changes the view, not the identity of a territory.

The platform supports all three layouts below. The two rows nearest each player's home edge are deployment rows: the rear one starts with Mount parties and the next with pawn parties. A pawn party is an initially unmounted group of five members. The remaining rows provide the space over which the armies advance.

Three kinds of card banks
A bank is a visible set of positions around the battlefield where cards are stored or placed. These positions are outside the playable territories. They do not extend movement routes or generate territorial income merely because a card occupies them.
Each player has a Major Arcana bank immediately behind its rear deployment row, with one position aligned to each column. A Major Arcana is a card placed there to maintain an ongoing effect. Its physical card stays in that bank position. Its definition can affect the assigned column, the original Mount associated with that column wherever it travels, or both. The effect's written target rule determines who benefits.
Behind that Major Arcana bank is the player's Minor Arcana hand bank. A Minor Arcana is a generated resource card that can become movement Supply, colored Mana or its attached ability. The hand bank has nine public positions, one per column. A new card from a column replaces any unplayed card still in that column's hand position. Both players can inspect these cards.
An Enchantment bank runs along each player's own left side, with one position aligned to each playable row. An Enchantment is a placed card whose ongoing effect applies according to its definition, commonly to the corresponding row. A's left bank lies at the global C0 side; B's lies at the global C10 side. The initial arrangement supplies one row position per player, while card rules can add positions or define permitted combinations.
Including both side banks and the two rear bank rows for each player, the complete rectangular frame is 11 columns by N plus 4 rows: 11×13 for the nine-row field, 11×14 for the ten-row field and 11×15 for the eleven-row field. Corner padding is not additional playable territory. In code, identify banks by owner, type and row or column rather than treating their diagram positions as ordinary terrain cells.
Member positions and the party center
The three-by-three member arrangement has a center and eight surrounding positions. A Mount occupies the center when present. An unmounted pawn party still has a geometric center even though that member position is empty. This center anchor determines the party's column and forward position for command eligibility and income. Individual retainers can reach into neighboring contact spaces without changing that anchor.
The interface must show the small positions, the actual members occupying them, the party's center and its current direction. A player should be able to inspect a partly moved formation and see which members remain exposed. The center is not required to stay at the exact center of a large territory while moving; it can pass through any of its local positions. The implementation stores this continuous position and a consistent assignment to the large grid, as described under movement.
4 Ticks Rounds and public orders
What a Tick and a Round mean
A Tick, also called a Count, is one game step. Both players make eligible decisions for that step, then the simulation advances movement and combat. A Tick is a rule unit rather than a fixed amount of real-world thinking time. Public planning and response choices pause the rules clock; continued travel advances only when the next agreed simulation interval runs. The display can animate its result quickly, slowly or frame by frame without changing the outcome.
Certain columns are highlighted during each Tick. Those active columns determine where parties may receive new movement, Spell and Skill commands. A Spell or Skill is a card-defined action with a cost, target and effect. Existing movement and battles continue across the whole board even when their columns are not highlighted. Highlighting concentrates new decisions without freezing the other armies.
A Round is the nine-Tick interval from one center activation to the next. The match begins with a four-Tick prologue before the first center activation. The exact opening schedule is:

The outer pair intentionally appears on two consecutive Ticks. During a complete Round, every ordinary column activates twice and C5 activates once. With one normal resource per player per active column, that is seventeen generated cards per player per Round when all columns qualify. It is a production total over time, not seventeen simultaneously stored cards.
Minting happens before new actions
Minting means creating a new match instance of a resource card. At the start of a Tick, mint the active columns' resources from the completed board state left by the previous Tick. New orders, movement and newly placed production effects cannot retroactively change that ordinary mint. An effect can create another production event only if its definition explicitly does so.
For example, C4 is active on Tick 4. Its income is calculated before a party moves forward during that Tick. C4 next activates on Tick 6, so its next ordinary card reflects the resulting advance if the party remains eligible. The player does not have to wait until the following complete Round merely because the schedule uses the word Round.
The proposed executable phase arrangement is: mint and replace bank cards from the prior state; clear old unspent pool Mana before any spending; let both players prepare public commands; agree those commands; resolve the declared resource uses and effects; advance movement and combat; then finish the state and terminal results. Minting and boundary cleanup form one transaction, with no opportunity to spend a replaced card between them. The first iteration has public cards, public effects and public plans; later secret-card formats are separate work.
Card durations must name their boundary. An effect lasting until the end of a Round ends with that period, while an effect lasting nine Ticks has an elapsed duration. The completed previous state must already reflect effects whose duration has ended before the next ordinary mint. This is a timing field in the card definition, not a question the renderer answers by finishing an animation.
Which instructions are allowed
There is no numerical gameplay cap on orders. The resources, legal targets, movement capability and time required by each action determine what the orders can accomplish. A large number of submitted instructions cannot create extra elapsed Ticks or spend one card twice.
For the first executable profile, inspect the party center's column at the planning boundary to decide whether it may receive a new movement, Spell or Skill order. Explicit formation changes use the same active-column check in this profile. These are unit orders. Resource administration is separate: a player may use any occupied hand-bank slot, and may deliver Supply to a party in any column and any state. The column where a card was produced does not restrict the recipient of its Supply.
A moving, turning or engaged party can receive Supply. An unmounted pawn party can store Supply but does not gain an ordinary movement pattern until a Mount joins it. Resource operations occur in the agreed game sequence; their permissive targeting does not let one client change the simulation halfway through an unagreed animation.
A party has one target destination. Replacing its movement order replaces that destination, rather than appending player-selected waypoints. In a command plan containing several valid destination updates for the same party, the final accepted update is the target. Other legal actions remain possible, and continuing travel retains its target until arrival, replacement or a rule that ends it.
5 Territory resources and card use
Two resources with different jobs
Supply is a party's remaining movement allowance. Moving one board square normally consumes one Supply. Mana is a temporary collection of colored amounts used to pay magical costs. A resource card can offer both values, but the player must choose which use to take from that particular card.
A Minor Arcana also has a printed rank, such as 2 or 4, a suit such as Wands, and an attached ability that can be played instead of using its resources. The card's definition is the reusable design in the player's collection; the generated instance is the individual copy currently available in this match. Replacing or consuming the match instance does not erase the reusable design.
Separate rank, Supply and Mana fields let effects change one value without rewriting the board engine or coupling deployment Supply to Mana production.
Finding the income-producing frontline
The frontline of a column is the furthest qualifying friendly party still connected to home under the column's logistical rule. The first executable rule scans from a player's home edge toward the enemy. It finds the first qualifying enemy center, then chooses the furthest friendly center before that blocker. A friendly party beyond the blocker is cut off and cannot extend that column's income. An enemy can block even when that enemy is itself cut off from its own home.
Center position determines this test. An enemy center in any of the column's three local files can block it; merely extending a retainer into the column cannot. Compare exact forward positions, so a center in the homeward part of the same large territory can be behind another party. An empty pawn center still supplies its anchor, letting the initial pawn line at home-relative row 2 establish opening income before Mounts merge with it.
On a ten-row field, suppose A has parties at R2 and R7, while B has parties at R5 and R9 in the same column. A scans upward and meets B at R5, so A's R7 party is cut off and R2 becomes its eligible frontline. B scans downward and meets A at R7, so B's R5 party is cut off and R9 becomes its eligible frontline. Both fall back to their second row from home.
Ground exposure determines logistical blocking
An enemy blocks supply only when its center occupies an exposed ground surface. A flyer above a column cannot cut the ground supply line by flying overhead. An enemy in a tunnel with intact ground above it does not block that surface line either. An enemy standing at the bottom of an open pit can block because it occupies a ground surface exposed from above. A grounded unit on a raised hill can also block.
This requires more than checking an elevation number. The implementation checks whether the center is supported by terrain, whether the party is airborne, and whether solid terrain forms a roof above that local position. Two enemies at the same negative height can have different results when one stands in an open excavation and the other in a roofed tunnel. The proposed first profile applies the same exposed-ground test to friendly income-producing frontlines; generation by other movement modes remains an extensible profile setting.
Calculating Supply and colored Mana
The proposed diagnostic profile uses the home-relative frontline row as its Supply basis. Its printed rank is that row number, limited to 10, and its base Supply equals the rank. Mana is calculated separately by adding the configured contributions of Mana-enabled rows between home and the frontline. This is an executable starting table, not a permanent balance formula.

A hand-authored rank-4 card with three Red and one Green can separately test resource choices without claiming that this territory table generates it.
Record the origin of each Mana contribution. If a row effect doubles only R6's one Green contribution, three Red plus one Green becomes three Red plus two Green. An effect targeting the entire card would produce a different result. The effect definition names the target and calculation stage; a client does not infer them from a vague visual highlight.
The public hand bank and replacement
Each active qualifying column normally mints one resource for each player. Paired Ticks therefore produce up to four instances across the match; the center produces up to two. Place each player's instance into that player's hand slot for the source column. If the slot is occupied, retire the old unplayed instance and replace it immediately. The old card cannot be rescued after the player sees the new mint.
With no spending, the first five Ticks fill two, four, six, eight and finally nine hand positions. Subsequent ordinary mints replace occupied positions. There is no separate seven-card discard procedure in this initial bank model. If a column has no eligible producer, the diagnostic rule performs no mint and leaves its previously stored card unchanged. An explicit effect can replace that behavior.
Using a bank card empties its slot. A card moved to a party as Supply, burned into Mana, or deployed as an Enchantment is no longer waiting in the hand slot and is not erased by the next mint. Those uses create their own state. Materials such as mined Metal belong to the material inventory; they do not consume these column-bound Minor Arcana slots unless a format explicitly changes the storage rules.

Mana expiry Rainbow and bounded storage
Burned Mana enters a pool: a set of amounts available for payment during the current Tick. Paying a cost subtracts the assigned amounts. Unspent ordinary pool Mana is unavailable in the next Tick unless a card explicitly permits carryover. A stored unplayed card and a loaded Supply allowance follow their own rules; neither is simply the Mana pool under another name.
Rainbow is a real resource that substitutes for ordinary colors. A cost of three Blue can be paid with three Rainbow, or a permitted mixture such as two Blue and one Rainbow. A cost expressly requiring Rainbow can only use Rainbow. For a cost of three Blue plus one Rainbow, the payment must reserve one Rainbow for that requirement before assigning any remaining substitutions.
Replacement prevents saving repeated outputs from the same column. Two successive C1 mints containing three Red cannot coexist in C1's single bank slot. It still permits combining different visible slots. C1 can hold three Red while C5 holds three Rainbow; burning both can pay a four-Red Spell without invading. That is a bounded interaction between selected storage and wildcard rules, not an additional invasion restriction.
Under the plain ten-row configuration, holding the full friendly Mana depth in all nine columns can store three of each ordinary color plus three Rainbow, totaling 27 Mana across the bank. Production modifiers, enemy-origin resources and other row configurations change that capacity. Loaded Supply can accumulate across replacement cycles because the player has already chosen the logistics use. These are behaviors to measure during playtesting rather than reasons to add unrequested caps.
Implementing replaceable generation rules
Before a match, agree which reusable ability definition each column and rank generates. The initial template bindings are copied on mint. Later selection policies still return a card instance with owner, source column, rank, Supply, colored Mana, attached ability, creation Tick and contribution provenance.
Record replacement with both the retired and new instance IDs; history does not keep the old card playable. Multiple mints into one slot apply in declared order, leaving the last occupant. A Card may instead provide extra slots or another supported destination, but must specify that policy explicitly.
6 Parties mounts and movement
The player moves a party but fights with its members
A territory is a large square on the battlefield. Inside it are nine visible member positions arranged in three rows and three columns. A party is the group of characters occupying those positions. A member is one character with its own identity, role, equipment and place in that group. This distinction matters because a party can move as a formation while individual members fight at its edges, assist a neighboring party, or advance through a hole in an enemy formation.
The middle position is the center slot. It normally holds the party's mount or leader. The other eight positions hold retainers. A mount gives the party its movement capability and chess movement pattern; it is a game role, not a requirement that the character ride an animal. A Commander is a specially designated center whose death can end the match. A Queen or King is a movement type. Those concepts must be separate in the data, so an ordinary King does not accidentally acquire the Commander's loss condition.

Starting parties and merging
A Pawn party begins with five retainers, an empty center slot, and no ordinary party movement. It still has a positional anchor at the empty center. That anchor lets the engine locate the party consistently for territory, effects and commands. A mounted party begins with its center and up to three retainers. When the mounted party moves onto a compatible Pawn party, their members combine under that mount. The resulting party contains six to nine members; it is full only when all nine positions are occupied.
Members keep their identities, damage, equipment and history through a merge. The merge must not create a tenth position, duplicate armor, or heal anyone incidentally. The demonstration placement policy preserves the mount in slot 5, keeps nonconflicting occupied slots, and places displaced incoming retainers in the first available slot in numerical order. Preview this result before accepting the move. More specialized cards may replace that placement policy.
A merged party cannot freely split apart. Separation or exchanging retainers requires an appropriate card, Skill or other declared ability. In the diagnostic profile, losing an ordinary mount disables its survivors' ordinary movement until another effect provides leadership; their anchor and positions remain. Losing the designated Commander instead activates the victory rule described below.

Opening deployment and merging
Each pawn party begins with five members and an empty center. Each Mount begins as a central member with zero to three additional retainers, as specified by its starting definition. When a Mount party moves onto a friendly unmounted pawn party, they combine. The resulting mounted party has six to nine members and gains the Mount's movement pattern. It remains combined unless an effect permits separation.
On the opening Tick, each player receives two zero-Mana 2s of Wands. Loading them into the two Castles gives each Castle two Supply. Each can move one square forward onto its pawn party. That one-square movement uses one Supply, leaving one on each combined party. A target at the pawn square ends the travel there; a farther legal target retains the remaining journey.
Merging preserves member identities, health, equipment and unspent Supply. It does not create a new healed copy of every character. The implementation resolves conflicting member positions using the agreed formation-placement rule while retaining each member's identity.
Facing travel and a Knight route
Facing is the direction the formation treats as front. A deliberate facing or formation change initially takes one Tick and no Supply. An east-facing Queen ordered west first turns, then begins westward travel on the next Tick. Effects may change that time. In the proposed route model, the bend already included in a Knight's L route does not add another administrative turn Tick; an explicit reversal or formation change still uses the ordinary delay.
For example, a Knight at R2C2 targets R4C3. The diagnostic route goes through R3C2 and R4C2 before reaching R4C3: two steps along the longer axis, then the short step. Starting with three Supply and already facing its first leg, it travels two steps during one unobstructed Tick and the final step during half the next Tick. It continues even if its column is no longer highlighted.
If an enemy blocks an intermediate territory, the Knight attacks and fights there before continuing toward its target. An attack along the route is not a new destination. The Knight does not leap over that enemy merely because its endpoint has an L shape. A special charge that strikes and continues without remaining engaged can later be expressed by a card; it is not assumed for ordinary travel.
Physical positions and partial Supply
The proposed physical fixture uses a territory body three member-width units across, a contact strip one unit wide, and neighboring centers four units apart. Members are squares of side one at offsets minus one, zero and plus one from the party center. A board step includes its strip and costs one Supply.
For corner assistance, this fixture lets an eligible helper extend locally into the contact strip without moving its party anchor or spending travel Supply. It keeps its home membership. If the neighboring party it supports retreats, the helper returns home; if its own party retreats while it is touching an enemy, the ordinary retreat casualty rule applies.
In that fixture, global territory centers have coordinates x = 4C minus 2 and y = 4R minus 2. A advances toward increasing y; B toward decreasing y. Logical row and column regions have width four. When a center lies exactly on a region boundary, retain its previous region assignment until it crosses. This gives both peers the same active-column and income decision while the formation straddles spaces.
Distance is continuous even though card loading uses whole instances. Record Supply in shared integer fractions and subtract the actual fraction traveled before contact or interruption. If a party travels three-quarters of a square, it spends three-quarters of one Supply. It does not receive that movement for free, and it does not lose a full point simply because an animation stopped early. The precision and rounding rule belong to the shared simulation profile.
Members' bodies determine contact. In the proposed body-and-gap geometry, an adjacent Knight moving at Speed 2 closes a one-member-width gap in one-eighth of a Tick. A Queen moving sideways at Speed 1 has shifted half a member width by then. The remaining overlap determines which flank members meet the attack. This is why the display must show the local formation and why collision cannot wait for the party to arrive at the next large-square center.
Replacing a target without teleporting
A new legal target replaces the old target; traveled distance remains spent. In this fixture, a party between traversal nodes finishes its current edge, then follows the replacement route validated from the next node. It neither teleports nor retains old destinations. Another profile can replace this declared transition rule.
Persist the target, route, position, facing, movement state, Supply and membership through each Tick. Combat pauses travel; clearing the obstruction allows it to resume. Both clients calculate the same motion and contacts, then animate and explain those results.
Physical routes and interception
A Knight selects an L-shaped destination and requires three Supply to complete the route. The initial route travels the two-step long axis and then the one-step short axis at Speed two. An enemy encountered along that route can be attacked even though its location is not the final destination. The Knight fights toward its destination, stopping while entangled and resuming when clear unless its order changes. A future charge-through card can authorize continued movement during an exchange; ordinary Knights do not receive that exception automatically.
The shared geometry fixture makes a territory body three member-widths across, with a one-member-width contact strip between neighboring bodies. Territory centers are therefore four member-widths apart. Each member has a physical square one member-width across. A normal logical square step includes the intervening strip and costs one Supply. Diagonal steps also cost one in this fixture. This geometry and its costs are editable profile data.
Contact must be calculated along the route, not only at square centers. Consider a filled Queen formation at row 5, column 5 moving west at Speed one while a filled Knight formation one row north moves south at Speed two. The initial physical gap is one member-width. The Knight crosses it after one eighth of a Tick; by then the Queen has moved half a member-width west. The Knight meets her partly shifted right flank. The exact time comes from these dimensions and occupied bodies, not from assuming the Queen must be halfway to her next square.
The simulation therefore needs each member's current position, home slot, party identity and movement progress. An empty slot changes the possible contacts. A retainer stepping forward does not move its party's center for territory income or Capital capture.

Six incoming faces and the meaning of protection
An attack reaches a defender from front, rear, left, right, above or below. These are six named defense directions, sometimes called a defense vector. Front is relative to the defender's facing. An arrow arriving from above uses Above protection even if the Archer stands somewhere in front on the map.
A shield can therefore protect the front without protecting the top. A new armor card might protect Above, several faces, or every face. Keep the incoming face, physical or magical channel, amount of protection, and area of protection as separate fields. A blue physical attack is still physical unless its definition says otherwise.
Protection also has a scope. Individual protection belongs to the recipient. Line protection collects eligible contributions along the attacked contact line. Cube protection applies within a stated occupied spatial cube. Party protection follows membership even when a member steps into a contact strip. These scopes must not be collapsed into one universal defense total. The Mage's party Magic Defense does not become physical shielding, and a helper does not automatically lend every protective effect of its home party to its neighbor.
Defense is applied to each hit separately. A hit of one against matching Defense one is completely stopped. Two such hits both stop. Two hits of two against Defense one lose one point each to protection and cause two damage altogether. Excess protection does not turn an attack into healing, and unused Magic Defense does not cancel physical damage. A physical hit of three against Physical Defense one causes two damage even if the recipient also has Magic Defense four.
Weapon definitions must preserve hit count, power, channel, range, eligible targets, incoming face, and any area-of-effect shape. Two one-point arrows are different from one two-point arrow because protection acts twice. A later card can explicitly combine or split hits, but the engine must not do so merely to simplify arithmetic.
Contact lines corners and breaches
A contact line describes a particular edge along which enemies are fighting. It records the touching members and eligible supporters, rather than simply saying two whole parties are adjacent. This makes front fighting, flanking and neighboring support visible and explainable.
An eligible corner member from a nearby party can help a fight at that corner. A flanking corner member can contribute to both the front and side engagements when it legitimately touches both. Count it once within each contribution scope, retain one identity and health record, and allow those separate contributions. A global rule allowing each member to contribute to only one line would remove the intended encirclement behavior.
With the prototype's one-member gap, neighboring corner helpers need a local step into the contact strip to establish that contact. The demonstration performs this during engagement setup without consuming simulation time, moving party anchors or spending party travel Supply; the UI animates and highlights the step. A blocked helper cannot occupy another body to provide support. Helpers retain their home party and home slot so damage and retreat can be attributed correctly.
Holes must change the next exchange. For example, place Swordsmen in slots 1, 2 and 3, Archers in 4 and 6, and a Queen in 5. If the Swordsman in slot 1 dies, its opponent advances into that position on the next Tick. It can then attack Archer 4 ahead and flank Swordsman 2, who is still fighting another enemy head-on. The demonstration permits one local member-slot advance without party Supply. It does not instantly cascade through several casualties in one exchange or move the entire attacking party's center.
Simultaneous exchanges and impact momentum
Enemies already engaged exchange attacks every global Tick, including when neither column is highlighted. Calculate the exchange from one common starting state and apply its damage together. A member killed by that exchange still delivers an attack it was entitled to make simultaneously. The order in which a computer happens to process the members must not decide who survives.
The demonstration gives newly touching parties an immediate exchange. An engagement-and-Tick marker prevents another ordinary exchange for that same contact in the same Tick. Later Ticks provide the normal recurring exchange. A weapon's two declared hits and legitimate contributions to distinct contact lines remain available. Animation frames and collision substeps never create additional attacks.
A charge changes the initial impact, using actual approach Speed at contact. In the initial physical-charge fixture, a Swordsman's Attack three at Speed two becomes a six-point impact hit. If both parties charge toward each other, each uses its own Speed. Their combined closing speed determines when they meet, not either attack multiplier. A defender moving sideways is not automatically charging into the encounter.
On the following Tick, entangled parties have no approach movement and use their ordinary Attack. The stationary Swordsman still attacks for three; multiplying that attack by zero would incorrectly make ongoing combat harmless. Slow terrain or an effect can change actual approach Speed before impact, so charge calculations must use the accepted motion state rather than a card's nominal Speed label.
For a complete Pike test, a stationary entrenched Pikeman facing a charge removes the charger's impact multiplier and uses that multiplier for its own physical impact attack instead. Its passage-blocking ability is a separate effect. This transfer interpretation is a configurable demonstration rule. Cards may define different charge channels, faces, entrenchment conditions or transfer operations without rewriting movement.
Four independent choices inside a combat profile
A combat profile is a saved set of rules used for a match or test. The platform must support the requested styles together rather than force a permanent choice now. Four independent properties make the differences understandable:
Hit structure says how many separate attacks a weapon produces. The starter Archer always produces two one-point hits before any explicit card modification.
Defense aggregation says whether protection comes from the individual recipient or the shared attacked line or other declared area. Protection still acts on each hit separately.
Allocation authority says who chooses among legal recipients: the attacker, the defender, or a declared automatic policy.
Health representation says whether damage reduces individual member HP or one party pool followed by a member-maintenance procedure.
Allocation timing must also be declared. With individual protection, select each hit's recipient before calculating that recipient's defense. Shared protection can be calculated first and surviving damage assigned afterward only within that same protection scope. If possible recipients have different protection, choose the recipient first or divide them into groups with identical applicable protection. Never calculate against one member and then move the result to another member to bypass its armor.

Each side has a Queen in slot 5, three Swordsmen in the front row, and three Archers in the rear row. Slots 4 and 6 are empty. The front Swordsmen meet in three opposing pairs.

A party health pool with member maintenance
The third requested style keeps physical members but replaces their authoritative individual HP bars with one party health pool. Members still have identities, positions, attacks and equipment. Damage reduces the pool; a maintenance rule decides which members can remain active at that health level. This can make casualties easier to manage while preserving formation holes.
In the diagnostic policy, a center contributes six pool HP and each retainer three. The example Queen with six retainers starts at 24. Reserve six for the center; every maintained retainer requires three points beyond it. After damage, keep only as many retainers as those whole three-point requirements support. Remove excess members in front, side, then rear slot order, with stable identity breaking ties.
Six damage leaves 18 HP. Twelve points beyond the center reserve support four retainers, so two are removed. This strict fixture also removes one after a single damage point at full capacity. That adjustable threshold is deliberate; other profiles can permit partial maintenance or use another resource.
Maintenance losses do not subtract damage again or reduce current/maximum pool HP. Maximum HP stays at the composition's initial capacity until an explicit recruitment, merge or capacity effect changes it. Healing cannot resurrect removed members. Merging adds remaining pools and capacities without healing. Display the pool, maintenance costs and casualty policy instead of individual HP bars.
The center lives while the pool exceeds zero; at zero the party is defeated. Six arrows over a Commander reduce a 24-point pool to 18 rather than killing a separate six-HP center. Explicit forced death, including its own contact retreat, can kill the center with positive pool health. Commander death ends the match. Forced deaths add no extra pool damage. An ordinary dead center releases its maintenance reserve and disables ordinary travel. Helper damage debits its home party's pool.
8 Retreat and victory
Retreat deliberately abandons contact. Before withdrawing, identify the retreating party's own living members actually touching an enemy. Those members die, whether they occupy front, side, rear or center positions. An untouched front member does not die merely because it is in the front row.
Helpers belonging to other parties return to their own formations alive if they survived the exchange. That protection applies when the supported party retreats. If a helper's own home party retreats while the helper touches an enemy, it is one of that party's sacrificed members. Returning home never resurrects a helper already killed by damage.
When the defender retreats, the attacker advances into the vacated territory. When the attacker retreats, the defender stays unless given a legal advance order and Supply. The demonstration resolves an exchange scheduled at the same timestamp before retreat, then applies retreat casualties. Ordinary retreat movement consumes normal Supply; automatic following of a withdrawing defender uses ordinary travel time but no additional Supply in this fixture. Competing followers use the common movement-conflict policy rather than a hidden preference for one player.
Each player has a fixed Capital at local row 1, column 5, where its Commander begins. An enemy party center entering that territory captures it; an isolated retainer does not. Moving the Commander leaves the Capital in place. Killing the enemy Commander is the other basic victory condition. Chess check and checkmate are not required.
Evaluate victory after every simultaneous event batch, including movement entry and casualties. If both players meet a winning condition in the same batch, the result is a draw. An earlier completed win ends the match before later travel can create another. In individual-health mode Commander death follows its own HP; in the pool mode it follows the explicit center-death rules above. This makes victory reproducible under every supported combat style.

Open ground tunnels and attack paths
Terrain must distinguish solid material from empty traversable space, with floors, roofs and connections between spaces. A single height value cannot represent a roofed tunnel underneath intact ground. Digging down from the surface creates an exposed pit; digging sideways from that pit can create a tunnel whose roof remains intact.

Travel requires a usable connection. A ramp and a cliff can have the same total height difference but demand different capabilities. Slower uphill approach also reduces an applicable charge because charge uses actual Speed.
Archer shots downward gain range and damage; shots upward lose them. For a complete diagnostic curve, use range two at equal height, add one range step and one power per hit when shooting downward, and subtract one of each when shooting upward, with range never below one and damage never below zero. These simple values are test settings. The weapon still produces two hits. Solid roofs and floors block attack paths unless an ability expressly penetrates them; being below an enemy does not authorize shooting through earth.
Mining creates resources and crafting creates items
At mining depth a party can uncover a mineral deposit. The starting resource is Metal, represented by a resource card when extracted. Each deposit has a stable identity and can be extracted once. Filling a pit and digging it again must not reset that deposit or produce another copy of its Metal.
A recipe describes how inputs become an item. The diagnostic recipe consumes one Metal and creates one armor item. Extraction takes one Tick, crafting one Tick, and equipping one Tick. The sample armor adds one frontal Physical Defense to its wearer. These numbers exist to demonstrate the entire loop; they are variables for playtesting, not settled balance.
Recipe data must state input types and quantities, output definition, work duration, legal actors, required position or facilities, equipment slot, and stat changes. Equipment modifiers state their channel, affected faces, scope and stacking behavior. The same structure can later produce artifacts or modify another property without placing special recipe checks inside combat code.
Record what was mined and what was made: deposit identity, extracting party, resource instance, recipe version, consumed inputs, output item identity, owner, time and location. Equipping and unequipping are separate events. Retrying an accepted extraction or craft cannot award a second resource or item. The client should let players inspect this history and the resulting equipment effect.
Long-term retention, loss after defeat and eligibility in future modes remain configurable development areas. The first implementation records and exports the results and can demonstrate importing equipment under an explicit local test profile. It does not require CJ to settle permanent progression, commerce or equipment balance before the mining and crafting capabilities work.

10 Cards Spells and changing the rules
A shared language for novel Cards
A Card is both an explanation for the player and a precise instruction for the game. Its text tells the player what happens. Its executable definition tells both computers how to produce that result. For example, “Your bound mount gains one front Defense while this Major Arcana remains in play” names a target, a statistic, a direction, an amount and a duration. Those facts must also exist as structured data. The software should never rely on two language models independently interpreting that sentence during a match.
The foundation must make new combinations possible. An ability that changes movement, a spell that creates terrain and a Major Arcana that follows its original mount should use shared targeting, duration and effect mechanisms. A new Card normally combines existing operations. A new kind of operation can extend the rules module in a later version. New prose alone cannot execute an operation neither client has installed; the content validator reports that specific missing capability before the match.
Design reference. Magic the Gathering lets specific Card text override an applicable general rule, provides shared timing and priority for responses, checks target legality during resolution, and distinguishes continuous effects from replacement and prevention effects. Its interaction rules also explain how overlapping effects are ordered. Those are useful foundations for an expanding Card library. The Hapa rules below adapt those ideas to public plans, territorial resources and simultaneous spatial combat; their exact phases and implementation choices are Hapa test settings. [R06 rules 101, 117, 608, 613 and 616]

Color is a selector and resource identity, not a universal damage formula. A Card's own color, the Mana used to cast it, its target's alignment and the color of the territory are different facts. “Reduce Blue damage” must select one of those facts in its definition. Physical and Magic are damage channels. A Red fire Spell can deal Magic damage; spending Red Mana does not silently make it Physical.
Rules that a Card can change
Implement movement permissions, command eligibility, resource production, stat contributions, targeting, durations, reserve capacity and victory predicates as queryable rules. Each query receives the relevant objects and gathers applicable effects. For example, asking whether a moving party can receive Supply returns yes under the base rule; a specific curse can add a prohibition that applies to that party. The UI should name the curse when it explains the prohibition.
The starting conflict convention gives a matching prohibition precedence over an ordinary permission. A Card that is intended to bypass a particular prohibition must express that exception explicitly through a supported rule operation. This is a declared Hapa implementation convention, not a limit on future Card ideas. Identity integrity, accepted message ordering and agreement on installed code are protocol properties: Card text can change a game cost but cannot silently authorize the two peers to execute different programs.
Keep effect families distinct. An immediate effect happens once, such as dealing damage. A continuous effect contributes while its source or duration remains active, such as extra Defense. A triggered effect is scheduled when a named event occurs, such as “after this party mines.” A replacement changes an event that is about to happen, such as increasing a minted card's Mana. Prevention reduces or cancels a specified consequence. Treating all of these as loosely ordered callbacks would make new combinations unreliable.
Color identities guide Card design
Colors express creative identities. They help players recognize a Card's theme, while its executable definition supplies the actual rule. A Red character does not automatically resist Red damage, and an Orange Card does not automatically amplify every effect. A later Card can define those interactions explicitly.

Public Spell responses
A response is an action permitted while another action is waiting to resolve. A counter Spell is one possible response. The pending action list is called the stack in the starting Card interpreter: a new response is placed above the action it answers, so the most recent pending response resolves first. This makes a counter to a counter intelligible. It does not change the simultaneous exchange of ordinary melee attacks into alternating attacks.
The starting response procedure is an engineering setting named public_stack_v1. After an ordinary Spell is announced and paid for, the opponent receives the first opportunity to respond. A legal response is announced and paid for, then the opportunity passes to the other player. If both players pass consecutively without adding another response, resolve the top pending action. If actions remain, the player holding first-action priority for this Tick receives the next response opportunity. A newly added response passes the opportunity to the other player; two consecutive passes resolve the new top action. If the list is empty, continue the ordinary action sequence. A pass means “I decline this opportunity,” not “I forfeit the match.”
Movement and combat do not advance while players edit an unresolved public plan or answer a response request. A response arising during simulation pauses at its recorded event time; resolving the response resumes that same event or interval according to its declared timing rule. Animation and time spent thinking do not consume Supply or grant additional attacks.
Card definitions decide which response opportunities they can use. A card may counter a Spell, prevent a Physical hit, react after a death, or state that it cannot be countered. A permission to respond does not automatically waive a colored cost or range restriction. The response definition can explicitly permit an action outside active columns when that is its intended rule. There is no global requirement that every Blue Card be a counter or that every counter have identical timing.
Ordinary actions from both locked public plans need a stable first order. The initial fixture alternates first action priority between Player A and Player B on successive Ticks, preserves each player's declared action order, and interleaves the two queues. Dependencies such as burning a card before casting must remain in the declared order. The transport does not use whichever packet arrives first. A format may later change this arbitration rule without changing how a Card describes its timing.
Costs are checked and consumed when an action is actually announced for execution. Planning previews account for declared resource claims, but a prior opposing effect can change whether a later action remains legal. Revalidate at execution. An action that cannot pay is rejected without paying; an action that was paid and is subsequently countered keeps its cost spent under the starting convention. Any refund is an explicit Card effect. A reaction may burn an otherwise unused public-bank card as part of its permitted payment procedure; it cannot reuse an instance already consumed elsewhere.
Worked response example. A player uses an attached Spell to damage an enemy member. The opponent answers with Blue Denial. The caster answers with another Blue Denial targeting that counter. Each Blue Denial consumes its own attached-ability card and pays two Blue from the pool, funded by other resource cards as necessary. The counter's own instance cannot first be burned for that payment. The last counter resolves first and removes the opponent's pending counter. The original damage Spell then resolves if its target remains legal. Every announced action, cost, target and pass is visible and recorded. A Card that says “cannot be countered” changes which counter operations can affect it, while prevention that acts on the eventual damage is still a different operation.
Applying several effects predictably
An effect needs a named place in the calculation. For ordinary numeric characteristics, the starting implementation reads the base value, applies explicit value-setting effects, adds or subtracts modifiers, applies multipliers, then applies declared limits and rounding. Within a stage, use explicit dependencies followed by creation order and stable effect ID as the final tie rule. If one effect changes whether another effect applies, reevaluate the dependent effect at the defined stage. Do not depend on JavaScript object iteration order.
This is an extensible calculation system. A Card can supply a special operation or an explicit replacement instead of being forced into a misleading generic numeric modifier. Replacement effects are evaluated against the event they modify, and the event records which replacements have already applied so the same replacement cannot repeatedly rewrite its own output. Where more than one applicable replacement creates a meaningful choice, the affected controller chooses one through a recorded public choice phase; reevaluate the remaining replacements afterward. The first fixtures include a deterministic standing choice so automated tests do not require a human prompt.
For example, beginning with one Mana contribution, an additive one followed by doubling produces four. A Card that explicitly doubles the original contribution and then adds one produces three. Both are possible definitions. The engine must expose the operations and their ordering, and the inspector must show the calculation actually used.
Mana production also needs an explicit target. On a frontier that includes three Red contributions and one Green contribution, doubling only the Green-producing row produces three Red and two Green. Doubling the entire generated payload produces six Red and two Green. The starter Mana Double example chooses the row contribution. A different Card may choose the whole payload. Existing modifiers participate inside the mint transaction using the completed prior state; ordinary new actions occur afterward. A newly cast production Enchantment therefore first affects a later mint unless it expressly creates resources immediately.
Durations use named endpoints. “Until the end of this Round” expires at the selected Round's end, while “for nine Ticks” counts nine simulation intervals. During the four-Tick prologue, the starting interpretation of “this Round” is the first upcoming Round; authoring tools must display that endpoint explicitly. An effect that should last until the next center activation can name that event instead. Store the chosen endpoint so peers never infer it from animation time.
Major Arcana location and effect binding
A Major Arcana physically remains in its assigned column reserve. Its effects may examine that column, follow a named mount, or do both. Those are separate bindings in one definition. At setup, an effect can bind to the mount that starts in front of the Card; that identity stays bound when the mount travels elsewhere. A region selector instead reevaluates eligible occupants of the column whenever the rule is queried.
Consider a Major Arcana behind C3 with two abilities. One adds one front Defense to its originally bound Bishop; the other adds one Mana to eligible production from C3. When the Bishop moves into C4, it keeps the bound bonus and the production effect remains on C3. A Knight entering C3 gains no Bishop bonus. If the Card also grants a column Defense effect, the Knight may receive that separate effect if its ownership filter allows it. The UI must display each binding separately.
The same selector system supports row Enchantments. The default board has one row slot and one column slot per player for each corresponding row or column. A territory can consequently lie in two row regions and two column regions, but each Card still decides its actual targets. Effects may add slots, prevent stacking or follow an entity. Reserve location alone does not determine every effect's scope.

A Card definition must state what happens if a target disappears or becomes illegal. The starting convention rechecks targets at resolution, affects the remaining legal targets, and produces no effect if none remain. An effect that needs an illegal target's position or value does not invent it; it uses a declared last-known-state rule only if that operation supports one. 11 Creating decks and sharing content
A deck is an agreed collection of usable definitions
In this game a deck describes the player's selected Cards, attachments, parties and permitted equipment. It is not necessarily a shuffled draw pile. Minor Arcana are normally generated from territory and placed into column slots. A future format may use a draw pile or finite copies; that behavior belongs to its deck and generation policy.
The first deck editor lets a player choose a Major Arcana for each column, select the starting roster, and map generated Minor Arcana to eligible attached abilities. The test binding policy maps owner, source column, suit and printed rank to one template. A fallback template can be used for unmapped ranks, including a resource-only card. Generation creates a fresh instance of that template and fills the source column's public slot. It does not delete the reusable template or consume a collection entitlement. An alternate generation policy can select among eligible templates through an explicit recorded choice or draw from a finite list.
This binding is data, not a restriction that every Wands card must have the same Spell. Two Wands columns can use different templates. A creator can make several rank-4 Wands definitions. The profile and deck state simply tell the running match which definition to instantiate on this occasion. Replacing a slot answers where a new card goes; the binding policy supplies what ability text it carries.
Exchange complete playable definitions before starting
Both clients must possess and understand both decks. A peer sends the definitions, their revisions, required operation versions, asset references and creator lineage. The recipient checks that it can execute all required operations and verifies the content hashes, which are fingerprints of the exact definition bytes. A missing cosmetic rendition can use an agreed placeholder. Missing game behavior cannot be replaced with a visual approximation.
The initial client retains received definitions in its local content catalog with creator and source information. This enables inspection, reuse in compatible test decks and later synchronization. Record receipt and actual use as separate events because they answer different questions about discovery and adoption. Detailed learning rewards, ownership restrictions and commercial entitlements are later policy work. They do not block a match or require the team to decide whether a received definition has crossed an educational mastery threshold.
Make creation understandable and testable
The creation UI starts from a known Card or a blank supported category. A player chooses targets, operations, costs, timing and duration, then sees generated rules text and a small preview scenario. Cost guidance uses editable curves and records which curve revision was used. The creator can save a draft, test it against bots or a partner, and publish a definition eligible for a selected experimental format. A new version receives a new content identity; an active match continues using the version it agreed at setup.
A mechanically valid Card can still be too strong or uninteresting. The validator checks executable meaning, required fields, legal operation types and configured execution limits. Playtests establish strategic effects. Do not present a successful validation as a balance certificate. The test dashboard should group results by Card revision and cost-curve revision so a later balance change does not mix incompatible results.
Player-created animations and images attach to rule events. An animation can show a fire burst, shield or charge, but the rules decide damage and contact timing. Use a bounded animation description or an approved asset format, with file-size and runtime limits declared by the content profile. Extending the animation vocabulary is allowed; executing arbitrary code supplied by an opponent inside the match process is not the default content mechanism.
Preserve authorship through reuse
Every definition and rendition carries its creator identity, source Hapa references and parent definitions when it is a derivative. A copied definition retains those fields. A modified version names its new contributor and its parents, so the interface can distinguish original authorship from later work. A match event points to the exact definition revision that acted.
Record creator statistics such as definitions created, matches in which a definition appeared, and uses by another participating identity. Human and automated identities can both contribute useful usage. The dashboard can filter controller type when comparing human comprehension with automated balance data. Count the same match event once even if both peers submit it, and label repeated experiments as repeated experiments rather than inventing independent people.
12 Player interface and visual explanations
Make the physical board readable
The player's main screen is the battlefield, not a spreadsheet of hidden calculations. It shows the nine columns, the selected number of rows, the three-by-three member slots inside every territory, and the reserve banks around the field. The hand bank and all Cards are visible to both players. At normal tactical zoom, the player must distinguish a center, occupied and empty member slots, facing, exposed sides and the next active columns. A zoomed inspector can add detail, but cannot be the only way to discover a gap in a frontline.
Use a stable angled camera for the pixel style, with an optional top-down tactical view. A formation's movement should remain trackable when the active-column highlight moves elsewhere. Highlighting a column communicates command eligibility; it does not visually dim or freeze combat elsewhere. A player can inspect every party, including an enemy party, because the first iteration has no hidden combat state.
The coordinate display must distinguish canonical coordinates used by the match from the player's home-relative view. For Player A, home-relative R1/C5 is global R1/C5; for Player B it is global R10/C5 on the ten-row field. Show the player's ordinary orientation by default and a clear canonical coordinate in the inspector or debug mode. Rotating the camera changes presentation, not territory identities, card targets or the event log.
Terrain height can obscure the information that matters. Provide layer selection, cutaway or transparency for a roofed tunnel, visible elevation labels, and separate icons for flight and walking on raised ground. An underground formation beneath a roof and a formation in an open pit can share a horizontal location but have different supply-blocking behavior. Selecting either must show which physical surface it occupies and whether it is exposed. Combat from Above or Below needs an explicit directional cue.
Make each card choice concrete
Each Minor Arcana slot shows its column, suit, number, Supply value, colored Mana quantities, attached ability and next scheduled mint opportunity, including whether the current state would produce a replacement. Hovering or selecting a slot opens the complete definition. The interface presents its mutually exclusive actions: supply a party, burn for Mana, or play the attached ability. After one succeeds, disable the other uses of that instance and explain where the value went.
Preview the source territory contributions of the next mint. For example, show “Supply 6; Red 3; Green 1” under a row-depth fixture rather than making the player infer Mana from the printed rank. If an enemy center cuts the column, draw the blocking position and the fallback frontline. The preview uses the known completed state and should be labeled as a forecast if subsequent movement or effects can change it.
Replacement is a visible event. When a column mints while its hand slot is occupied, animate the old instance leaving and the new instance entering, and record both instance IDs in the explanation. Do not silently move the old card to an unbounded personal hand. A production effect that changes reserve capacity or replacement behavior must show the resulting extra slot or new rule. A player should be able to predict when C1 next activates and whether it is currently expected to mint a replacement, including consecutive outer-column activations.
Commands and movement previews
Selecting a party highlights legal destinations for its mount and shows its current destination, route, remaining Supply and Speed. Choosing a new destination replaces the previous destination; the ordinary control must not create waypoints. A Knight preview displays the entire three-step L route and which enemies it will encounter. A blocked route should show that the party will engage and later attempt to continue, rather than depict a leap through the enemy.
Supply delivery is permitted to moving, turning, stationary and engaged parties unless a particular effect prevents it. Permit dropping a bank card onto a party or selecting the Supply action and then its recipient. The effect preview shows the complete Supply allowance added and the remaining distance at the current Speed. An unmounted Pawn party can receive and store Supply, but its preview must still explain that it needs a mount for ordinary movement.
Orders are public. Show each player's submitted plan, current plan revision and whether that player has frozen the plan with Ready. Before Ready, edits update the visible preview. When either plan changes, make clear that an old pair acknowledgment is no longer current. Do not use the old hidden-command or reveal language. A counter opportunity appears as a named response window with its eligible Cards, costs and Pass control.
Explain combat with members and directions
When two parties engage, show the actual contact strip and highlight contributing members. Draw separate incoming directions for front melee, flanking attacks and overhead projectiles. The combat inspector names each hit's source, damage channel, incoming face, applicable Defense, prevented damage and damage that remains. Use everyday wording: “This arrow deals 1 Physical damage. Front Defense does not cover Above. Damage received: 1.”
The selected damage mode changes the decision interface. In attacker-allocation mode, the attacking player chooses among eligible defenders. In defender-allocation mode, the recipient chooses how the allowed damage is assigned. In aggregate-health mode, show the party's shared health and the maintenance rule that removes or disables members when capacity falls. The interface must not pretend the third mode is simply a different name for individual member health.
A melee exchange is simultaneous even though the replay may animate it in a readable sequence. Display an exchange identifier and a shared timestamp. A member killed by the exchange still delivers any hit it was entitled to make in that same exchange. A charge explanation shows the approach speed used at contact and then shows ordinary Attack on the next stationary exchange. A retreat preview marks the retreating party's touching members as losses and identifies neighboring helpers that return alive to their own parties.

13 History learning and progression
Record experience before deciding every reward
The game creates a lasting record of what happened: which Cards were used, which members contributed, what terrain changed, what was mined and what was made. These facts remain useful while progression policies change. A playtest can compare two crafting recipes or two equipment-persistence rules without rewriting the underlying mining event.
An event has a stable ID, a match ID, a Tick or choice phase, the acting participant and relevant source identities. Its payload records the actual state change. A mining event names the deposit, amount, material type and recipient. A crafting event names the recipe revision, consumed inputs and produced item. A damage event names the source Card and members, target, face, channel and actual health reduction. Where aggregate health is used, distinguish shared-health damage from individual casualties instead of inventing per-member damage that did not occur.
When both peers copy the same event or a replay is imported twice, the history system applies that event once. This property is often called idempotence. It prevents one completed extraction from creating extra Metal because a reconnect retransmitted the record. It does not prevent legitimate repeated experiments or automated matches from contributing additional distinct events.
Statistics that explain play
Store matches and outcomes by profile, board, deck revisions, controller types and random seeds. Track member-type performance, damage dealt and received, casualties, support contributions, movement, resource generation and consumption, casts, retreats and time spent engaged. Keep raw damage, prevented damage, actual health loss and overkill separate when useful. They answer different questions about balance.
Record creator use separately from combat credit. A Swordsman may deliver a hit, a Card may supply its bonus, a neighboring member may contribute Defense, and a creator may have authored that Card. Those identities should not collapse into one score. An aggregate report can count all four dimensions while the event itself remains one occurrence.
Human and automated matches are valid data under their declared protocol. The report should identify participant type so a designer can distinguish evidence about strategic balance from evidence about human comprehension. A bot's ability to operate a complicated rule is not evidence that the human interface explained it. Conversely, an automated match is not dismissed because no human made its moves.
Make persistence a selectable projection
A progression policy reads the event history and decides which outcomes a later format imports. For example, a policy may carry crafted armor forward, reset its combat benefit but retain its provenance, or start every test with a fresh loadout while retaining the experiment record. These are different views of the same recorded events. The software must support changing that policy without deleting the history of what was mined or made.
The initial development profile retains complete local event history and item records, then uses explicit setup data for each new match. It does not automatically treat every historical item as equipped in every future match. A separate persistence experiment can choose which items to import. This supplies a working default while leaving final retention, durability and progression values for playtesting. Card definitions and recipes remain inspectable after the match.
Quests and milestones can be rules over identified events: a Priest contributes a stated amount of damage, a player uses a received ability, a creator's definition appears in a specified number of matches, or a party completes a mining-and-crafting sequence. Store the quest definition and version alongside its progress. Values, eligibility rules and rewards are editable profile data. The platform should make them testable rather than demand a permanent achievement economy before the first playable match.
Learning through play
The first learning objective is practical understanding. Can a player explain what a Card does, why they spent it on Supply instead of its ability, why a shield failed against an overhead attack, or how a Major Arcana continued to affect a moving mount? The interface and replay supply explanations; observation and playtest feedback establish whether those explanations work.
Retain received content and its attribution because both clients must understand both decks. Later curriculum, mastery conditions and discovery rewards can build on receipt and use events. They are not additional access gates in the initial game. The Hapa purpose is supported by useful, understandable Cards and reusable experience even before a formal educational program exists.
14 Configurable profiles and test data
Why the rules live in named configurations
A profile is the agreed setup for an experiment. It specifies board layout, resource production, movement geometry, damage policies, roster values, content, controller behavior and import/export policies. A profile can be complete enough to run while all its balance values remain provisional. This is how the platform supports experimentation without forcing each subsystem to guess what another subsystem assumed.
Use one base starting profile and derive alternatives by changing named fields. Give every revision a readable name, a stable identifier and a content hash. A match records the exact revision and cannot silently pick up a later edit. In the editor, each field has a description, units, legal values, a starting value and the reason it exists. Advanced settings can be grouped, but they must remain available to the experiment runner and content tools.

Excavation permissions, movement connections, deposit yields, recipes, equipment modifiers and action time.
Test mining and equipment behavior before selecting final numbers.
Progression
Which recorded events contribute to progress and which prior items a match imports.
Compare persistence policies without erasing provenance.
Automation
Bot revision, policy parameters, seed set, seats and run budget.
Reproduce a result and distinguish controller changes from rules changes.

What a profile validator should reject
The validator checks completeness and consistency, not whether the designer made a strategically good choice. Reject an unknown damage policy, a template referring to a missing operation, duplicate entity IDs, a negative ordinary movement cost, an impossible slot assignment, or a missing named recipe parameter. Accept different legal defense values, supported damage modes and experimental cost curves even when they may prove unbalanced.
A diagnostic fixture can directly create a specified combat or resource state without pretending that it emerged from ordinary play. Label it as a fixture. For example, a manually supplied 4 of Wands with three Red and one Green is useful for testing mixed payment; the territory-production fixture separately proves what its current frontier curve actually mints. This lets the platform preserve the supplied examples while comparing generation configurations.
The full starting-profile appendix supplies one executable set of temporary choices for every system used by the first match. Agents can implement and run it without obtaining final balance decisions from CJ. The remaining alternatives are named capabilities and experiments. Implementation reports must identify which modes are implemented, which have test fixtures and which remain scheduled work; a dropdown with an unimplemented option does not count as supporting that experiment.
15 Software architecture and the Lumina fork

Figure 3 The proposed software structure. The shared rules calculate outcomes for humans, bots, each peer and replay. Lumina displays the resulting state; the peer adapter exchanges public inputs and signed records. Each participant runs its own copy without a central match referee.

The game needs one set of rules that can run in three situations: a person playing through the pixel-art interface, two computers checking the same match, and automated players running experiments. Build that shared rules module first and connect the other parts to it. This makes a balance experiment exercise the same movement, cards and combat as a visible match.
A rules module calculates what happens. A renderer draws what happened. A controller chooses what a participant wants to do; it can be a person, a scripted bot or an agent. A peer is one participant's application, which exchanges messages with the other application. A record stores the commands and resulting events so a match can be reproduced. Keeping these responsibilities separate allows the interface, networking and automation to evolve without creating different versions of the game.
The first game iteration has fully visible decks, cards, commands and effects. Each peer independently checks the rules. There is no centralized match server or privileged host. Automated players are legitimate participants when their commands follow the selected protocol. Cryptographic traps belong to a later game iteration. That future iteration is separate from this requirements document's version number. [U03]

The shared rules module and its interfaces
A match profile is a named, versioned collection of settings for one experiment: board dimensions, income rules, movement, combat allocation, card costs and any other parameter that changes outcomes. A fixture is a concrete starting situation with explicit settings and an expected or inspectable result. Temporary fixture values make software executable while leaving final balance open.
The rules module receives a profile, complete card definitions, an initial state and accepted commands. It returns the next state and an ordered list of events explaining changes. One Count, also called a Tick, is one game step; it can contain intermediate movement and several choice phases. Deterministic means the same inputs produce the same outputs. Both players and a replay must therefore agree on ordering, coordinate precision and any random sequence. Frame rate and network delay cannot change who was hit.
Use integers or another explicitly specified numerical representation for authoritative positions, resources and time. For example, dividing a territory into a fixed number of simulation units permits exact local-slot positions; the chosen number is an engineering setting recorded with the rules version. Do not read the wall clock or call Math.random inside the rules. If gameplay requires randomness, store its algorithm, seed and current position in the state. Decorative particles can use independent randomness. Lumina's 32-bit hashString helper is for seeded procedural work; use the chosen cryptographic hash implementation to identify signed match data. [LUM09; proposed implementation]
The following API names are proposed contracts to implement, not existing Lumina APIs. All inputs and outputs must have schemas: documented field names, types, meanings and version identifiers.

Recreates the initial state and applies recorded inputs; reports whether calculated events and state fingerprints match the record.
projectHistory
Turns identified events into statistics and crafting history. Processing an event twice has the same effect as processing it once.

A phase is a named point at which the rules either calculate something or wait for an eligible choice. A spell response and a player's damage allocation can therefore request another phase without embedding a user-interface dialog inside the rules. A request includes a unique choice ID, eligible participant, valid targets and options, and the state to which it applies. The response travels through the same protocol whether a person clicks or a bot chooses.
Keep party identity, member identity and position separate. A center determines the party's location for the selected territory rule, while a member can contribute to a contact elsewhere. Preserve a party's one current destination when movement stops to fight. Resupply is accepted in any state unless a card says otherwise. Record approach speed when contact occurs so the charge bonus does not persist into a stationary exchange. These facts must be accessible to the rules without reading sprite positions. [U03]
Terrain also belongs to rules state. Store solid material, traversable space, exposed surfaces and each occupant's movement mode. This distinguishes an open pit from a roofed tunnel and implements the selected exclusion of flyers and covered tunnels from supply blocking. Lumina's existing surface-height format is useful for drawing terrain, but cannot alone represent overlapping underground space. Translate the game's column, row and height into the engine's horizontal X/Z coordinates and vertical Y coordinate at the presentation boundary. [LUM04, LUM05, LUM06]
Connecting the rules to the pixel battlefield
The presentation adapter is a small translation layer between the rules state and Lumina objects. It creates or updates meshes, sprites and labels for identified game entities. Input works in the other direction: a click on a territory becomes a command containing a territory ID and destination, which the validator checks before acceptance. Dragging a sprite must never directly move the authoritative member or change its resources.
Within a Count, the rules determine movement and contact at intermediate times. The renderer follows those resolved trajectories while drawing as many frames as the machine can provide. Existing movement continues outside highlighted columns. The active-lane highlight tells the player where eligible new orders may be issued; it does not stop the rest of the battlefield.
A visible three-by-three grid and member-level inspection are part of implementing the feature, not polish to add after combat. Display the center, individual bodies, facing, contact faces and terrain layers clearly enough to explain a result. Rendering a single icon per party would omit the information needed to understand flanks and incoming attacks from above. The UI chapter defines the detailed controls.
Upstream generates its image and audio content procedurally. Player-created Hapa animations therefore need a deliberate asset-loading extension. Transfer assets with exact content identifiers and creator references, and connect animation cues to rules events. A missing optional visual can use an agreed simple replacement; an unknown gameplay operation cannot silently acquire an invented effect. Animation duration does not determine damage timing. [LUM01, LUM04]
16 Peer play public information and automation
Identity logs and connections in plain language
A DID, or decentralized identifier, names a participant and links to a document describing how its control can be verified. A digital signature lets the receiver check that a statement was authorized by the corresponding key. The DID method specifies how that identity document is obtained and interpreted. Hapa's adapter must bind the participant's DID to the keys used for this match. A software participant can use an identity; the game does not require proof that a human personally chose each move. [P06]
Hypercore supplies a signed sequence of data blocks that can be stored locally and copied between peers. In this game, each participant writes its own log; the other reads and retains that log. Commands, accepted choices and receipts are application records inside the blocks. Hypercore verifies log data; the Hapa rules module still checks what those records mean. A receipt is an acknowledgment naming the exact record or state accepted. [P01]
Hyperswarm helps peers find each other and establish encrypted connections, using HyperDHT underneath. Encryption protects network traffic; both participants still receive visible gameplay information. Use configurable peer discovery and optional peer forwarding without one mandatory vendor endpoint. Connection infrastructure must not become a central match authority. No remote service selects legal moves or awards victory. [P02, P03]
Each peer keeps separate storage and keys, including when both run on one development computer. A test coordinator may launch processes and collect reports; both peers still run the validator and state transition. This permits convenient local automation without making one process the referee.
Agree exactly what is being played
A match manifest is the complete agreement both peers accept before play. It records the match ID, participant seats and identity bindings, log keys, protocol version, profile, initial forces, both decks, required assets, rules interpreter version and any random seed. A content hash is a fingerprint of exact bytes. Including those fingerprints prevents two peers from unknowingly using different revisions of a card with the same name.
Both clients must possess and understand both decks before accepting the match. Transfer missing definitions and assets directly, validate them, then accept the manifest. Pin active-match content: a newly shared balance revision applies to a later experiment, while this match and its replay retain the definitions they started with. Future entitlement policy does not block exchanging the required deck data now. [U03]
For integrated Hapa participation, each participant also publishes a signed match-intention record to its public DID-associated Hypercore. The record names its DID, opponent, match ID, deck fingerprints, agreed protocol and the new match-log keys. This is a public check-in and discovery record, not a centralized registry or referee. Independent participants can publish and replicate their own announcement feeds. Local fixture identities exercise the same record shape with their clearly labeled development keys; the identity adapter supplies the actual Hapa DID binding when that integration is available.
Proposed first public planning fixture
Fully visible planning needs a timing convention. The following is a replaceable implementation fixture, not a claim that CJ selected permanent response timing.
Both peers calculate the new Count's mint from the previous state. They display all current resources, effects, destinations and new command proposals.
Each participant publishes its plan with a monotonically increasing revision number. Before pressing Ready, it may replace that plan. A movement command changes a party's one destination rather than adding a waypoint queue.
Ready names the Count, phase, prior-state fingerprint and exact pair of plan revisions reviewed. The participant's first Ready freezes its own plan for that phase. It cannot silently change those orders afterward.
The other participant may still be editing. If it publishes a different revision, a Ready acknowledgment of the earlier pair becomes stale. The already-ready participant must acknowledge the new pair, while retaining its own frozen plan. The UI shows which exact plans each player accepted.
Both peers resolve only when two valid Ready records name the same pair. This matching pair is locked. Later messages cannot revise that resolved phase. A subsequent choice phase opens fresh plans as the rules permit.
This is open planning: seeing the other plan and responding before Ready is allowed by the fixture. There is no command concealment or commit–reveal step. An empty plan is a legal pass when the rules permit it. Ready freezes a plan, not a quota of gameplay actions; the absence of an order cap remains intact. A future mutually agreed reopen control can change the planning experience without changing card mechanics.
For card-authorized responses, use an explicit priority token: it identifies who may add the next response or pass. The Card interpreter supplies the initial recipient. In the starting fixture, the opponent of an announced Spell receives the first response; ordinary action queues use alternating first seats by Count. A response is recorded, resets the pass count and transfers priority. Two consecutive passes with no intervening response resolve the most recently added unresolved effect, then reopen priority if effects remain; two passes with nothing waiting finish the response phase. The interpreter determines which effects allow responses and when costs and targets are checked; transport carries those choices. Additional responses can themselves be eligible targets. Packet arrival order never grants priority.
Records checkpoints and ordinary recovery
Every accepted message includes schema version, match ID, author, sequence number, Count, phase, prior-state fingerprint and payload. Record the exact plan revisions and choice IDs. A repeated message with the same identity has no second effect; conflicting content under one identity is reported. Both peers calculate the resulting events and sign the state fingerprint they obtained. A checkpoint stores that agreed position so the application can resume without replaying everything from the beginning.
Proposed message fields are schemaVersion, type, matchId, authorId, authorSequence, count, phaseId, priorStateHash and payload. A Plan payload contains planRevision and commands; Ready identifies both plan revisions and their fingerprints; Choice identifies choiceId and its selected option; Receipt identifies the accepted record and calculated state. Sign the entire encoded message body. Specify one shared byte-encoding and hashing procedure so both runtimes sign and compare identical data, including object field ordering and numeric representation. Local timestamps may assist diagnostics but do not order the game.
Keep copies of accepted log records and the corresponding receipts. Hypercore exposes fork and truncation behavior, so the game must not replace an accepted match prefix with newly rewritten history. [P01] If a connection stops, preserve progress and show that the session is waiting or unfinished. On reconnect, exchange missing records and resume from an agreed checkpoint. Future forfeit, penalty and reward rules are deferred; deciding them is not a prerequisite for these basic recovery features.
A replay package contains the manifest, exact rules and content, accepted commands and choices, relevant log records, checkpoints and outcome. A verifier recalculates the match. Keep local copies and export support: P2P data remains downloadable only while some peer holds and serves it. Local offline replay can use already-held bytes. [P05]
Automation and balance experiments as product features
The same controller interface should support a person, a simple heuristic bot, a search-based bot and an external agent. A controller receives the public state, legal choices and current phase, then returns ordinary commands or a choice response. It cannot write HP, summon resources or bypass the validator. Humans and bots use the same visibility, costs, timing and victory rules.
An automated match that follows the selected protocol is a valid encounter and useful competition under that protocol. Record controller type and version to explain the data, not to disqualify it. A mixed human-and-bot match remains valuable for interface and strategy testing; bot-versus-bot batches make it practical to compare many card combinations. [U03]
Separate two automation modes. A rules experiment can run in one headless process, repeatedly applying controller decisions to the rules module. It is fast and useful for mechanic exploration. A protocol experiment runs two independent peers with separate logs and identity keys, using the same public planning and receipt messages as normal play. Label the first a rules simulation and the second a peer-verified match so reports accurately describe what was exercised. Neither requires a visible battlefield for every run; open selected replays in Lumina for inspection.
Each experiment records its profile, starting roster, decks, seeds, controller versions and decision budgets. A decision budget measures permitted work, such as candidate moves examined, so a result can be reproduced without depending entirely on machine speed. Alternate participant seats and run the same seed set across compared profiles. Log actual controller choices even when a controller itself is nondeterministic; replay depends on the recorded inputs.
Useful reports include wins, draws and unfinished runs; Counts to first engagement and outcome; territory gained; Supply spent; Mana produced, spent and expired; cards replaced unused in public hand slots; cast frequency; damage by channel and direction; casualties; mining; crafting; and profile-specific errors. Preserve per-match records behind aggregates. A win-rate difference can then be investigated through its cards, positions and choices rather than accepted as an unexplained number.
Do not make every run wait for final balance values. Put provisional recipe costs, unit stats and effect coefficients in the experiment data. Change them, rerun, and retain both versions. Bot results describe the tested opponents and conditions; combining varied bots with friends-and-family sessions broadens the evidence. A rejected command, mismatch or simulator failure is a diagnostic result and should not be mixed silently into wins and losses.
Upstream's sandbox/combat.play.json and sandbox/combat_play.js demonstrate fixed-step adventure-game automation. Its current hooks are documented in docs/specs/AUTOMATION_API.md. Reuse those techniques for screenshot and interaction checks, while implementing Hapa controllers against the new command API. There is no existing Hapa bot or batch-runner npm command at the inspected revision. [LUM16, LUM17]

Hapa is the surrounding system for identities, Cards, content, worlds and attributable experience. The game needs those concepts, but a new developer should be able to run it without first reconstructing every Hapa service. 18 Development sequence and acceptance
Begin with a working vertical slice
The first engineering objective is a complete, understandable experiment: load a profile and two decks, create the board, generate the opening cards, accept visible orders, move and merge parties, resolve a controlled battle and record an outcome. A vertical slice means that the rules, interface and record all work together for this small sequence. It is more useful than a large menu whose game options do not yet execute.
Keep that sequence running as the platform expands. Implement additional board sizes, damage policies, terrain operations and Card operations against the same contracts. Each capability needs an executable example and a visible explanation where a human is expected to use it. A placeholder can support parallel work, but the development report must name it as a placeholder.
This document supplies enough concrete test settings to start. Final balance values, progression permanence, hidden traps, commercial policy and disconnect penalties are not prerequisites. When a new interaction needs a temporary choice, put the choice in the profile, explain its observable result, add a small test, and retain the ability to change it. Escalate a genuine conflict with a stated product rule; do not ask CJ to choose every numeric coefficient before the underlying variable is implemented.
Repository and responsibility boundaries
Keep the generic Lumina engine usable by its existing application. Place Hapa-specific rules, controls and data in an application area such as src/hapa. The proposed rules module must run without WebGL or a browser document. It is the one implementation that people, bots, replay and peers all exercise. A renderer, bot or network handler must never maintain its own alternative combat formula.

At Tick 1, each player receives two rank-2 Wands cards with two Supply and zero Mana under the deployment-Mana-off profile. The cards occupy C1 and C9 public slots.
Same-column replacement
If C1 still holds an unused card when C1 next mints, the old instance leaves and the new one is the sole ordinary occupant. It never accumulates in an invisible hand.
Different-column payment
Two distinct occupied slots may contribute to one legal payment, including ordinary-color payment using Rainbow. The interface shows the exact cards consumed.
One consuming use
Attach, burn and attached-ability use each work in separate runs; trying to use the same instance twice fails deterministically.
Supply in every state
Stationary, moving, turning and engaged parties all receive Supply unless a named effect prohibits it. An unmounted Pawn stores Supply but remains unable to make an ordinary move.
Mana row configurations
Toggling deployment rows' Mana contributions changes their Mana production without silently changing the Supply curve.
Center cutoff
A qualifying enemy center behind an advanced party changes the next column mint. A stray retainer does not substitute for that center. A Pawn's empty-center anchor still determines its position.
Round boundaries
Ticks 1–4 are prologue, Round 1 is 5–13 and Round 2 begins 14. Ordinary columns mint on their next activation, which can occur within the same Round.
Persistent destination
A path continues outside highlighted columns and after a cleared fight; a new movement order replaces its destination rather than adding a waypoint.
Knight travel
The selected L destination requires three Supply, follows the declared route, contacts intervening enemies and does not leap through them by default.
Directional hits
Front-only Defense protects a front hit and does not reduce an Above hit. Two one-point hits against one applicable Defense cause zero; two two-point hits cause two total.
Mirrored Swordsmen
In individual-defense mode all six front Swordsmen receive two damage. Under shared line Defense three, each three-point hit is prevented.
Six arrows
Three Archers each make two one-point Above hits. With no Above Defense, six damage is available under the selected target and allocation policy.
Health alternatives
Attacker assignment, defender assignment and aggregate party health each have an executable fixture with defined casualty behavior and a matching explanation.
Charge impact
Approach speed modifies the declared impact exchange. The following stationary exchange uses ordinary Attack, not zero Attack or a permanent speed multiplier.
Corner and breach
A valid neighboring helper contributes with one identity; a casualty leaves a gap; a member entering that gap changes the contact faces without moving its entire party center.
Retreat
Only touching members belonging to the retreating party die from retreat. Outside helpers return alive to their own parties. Follow-up movement uses the declared fixture policy.
Victory
An enemy center entering the fixed Capital causes capture. Commander death causes loss. Simultaneous loss conditions can produce a draw.
Card exceptions
A Card can alter an ordinary permission, target a bound mount or region, and use its declared response window without hard-coded checks for its display name.
Two-peer agreement
The same complete input history yields the same state on both peers and replay. A stale Ready pair does not resolve a newly edited plan.
Automation
A bot receives only the same public game information and submits the same commands. Its valid match is reported as a valid automated match.
Terrain exposure
A live enemy center supported by an exposed ground surface can block column income. An airborne enemy or a center under an intact roof cannot. An empty excavation is not itself an enemy blocker.
Mining and crafting history
One extraction event and one crafting event retain their deposit, inputs, recipe and output identities. Duplicate replay import does not create a second award.
Content exchange
Both peers receive complete compatible definitions; a derivative preserves its creator lineage and original parent. Unsupported operations are named before play.

Required development handoff
The implemented repository must include a README that begins with what the game does and how to start one visible local match. It then explains how to run two peers, run a bot experiment, edit a profile, author a supported Card, replay a match and inspect its events. Provide a complete bundled catalog and fixtures; do not leave a new developer to locate a private service or reconstruct definitions from screenshots.
Document which commands already exist and which are new. A completed development report includes the commit, run commands, actual results, supported profile revisions, screenshots or a reproducible replay where useful, and known limitations. If a feature is only simulated or mocked, say which boundary is mocked. Preserve worthwhile later work as a named backlog item rather than pretending it is implemented or abandoning it.
19 Experiments and deferred decisions
Experiments the platform must make easy
Design questions become playable comparisons: choose starting values, run the experiment, and revise them. Final balance is unnecessary for beginning implementation.
Compare the three board lengths with the same forces and resource rules. Compare Mana-producing versus nonproducing deployment rows. Compare individual versus shared line Defense while keeping hit sizes fixed. Compare attacker assignment, defender assignment and aggregate-health maintenance using the same battle. Compare public-bank capacity and replacement behavior using the same decks. Compare crafting recipes and item import policies while retaining every extraction and crafting record.
Keep a named baseline and change one major setting at a time when useful. The experiment record states the question plainly, names changed fields, links runs and records tradeoffs. For example, “Does defender allocation preserve ranged members so reliably that melee positioning stops mattering?” can be investigated once the allocation modes work.
The public bank limits a player to the available slots and replaces successive output from a column. It still permits combining different columns, including Rainbow. Record unused replacements, time to first Spell and the sources of payments. Those observations show whether the chosen reserve system creates the intended pressure to advance. No additional universal invasion requirement is added by this specification.
Work deliberately left for later
Cryptographic traps and other hidden-card verification are outside the first game iteration. Unknown hidden effects are not a current design task. Keep ordinary visibility metadata extensible, but do not build a hidden-proof subsystem or make it a dependency of the visible game.
Final forfeit, penalty and reward adjudication after a peer interruption is deferred. The initial client preserves its records, reports the session as waiting or unfinished, and supports ordinary resumption. Likewise, learning entitlements, permanent equipment retention, durability and progression balance are deferred policy choices. The application must already record the events and expose the variables needed to investigate them.
Commerce, pricing, a fixed curriculum, broad hardware qualification and a final release scope remain open by choice. PC and Mac play with keyboard and mouse is the initial target. The team should measure actual friends-and-family hardware and improve observed bottlenecks. Future companion clients, new teaching themes and larger content sets can use the same explicit game and data contracts.
When a developer should ask a design question
Ask only when a proposed behavior conflicts with an explicit product rule or when no safe temporary configuration can demonstrate the capability. State the current behavior, a concrete scenario, the possible outcomes and why implementation would differ. Include a runnable proposed interpretation when possible. Do not send an isolated identifier or ask for a variable whose value can already be changed in the experiment editor.
For example, a Card that copies a mount while preserving its unique Commander identity creates a concrete two-center victory issue. Explain that conflict and propose an identity rule. An adjustable armor cost of one Metal or two requires a working variable, not a blocking decision.

Revision notes for version 3
This version is self-contained. The following notes record the changes that matter to an implementer without requiring an earlier document.
Explain each feature before its implementation. The document now defines the game objects, gives a complete opening walkthrough and supplies readable examples, interface expectations, source-based setup instructions and concrete engineering fixtures.
Make the first game fully visible. Decks, cards, submitted commands and effects are public. The starting Ready procedure agrees visible plan revisions. Hidden traps and their verification are later work, with no mandatory commit–reveal dependency in this game iteration.
Store generated cards in column slots. Each player has nine public Hand slots behind the Major Arcana row. A new mint replaces the unused card in the same column. This supersedes an unrestricted hand or a separate seven-card discard rule.
Separate resource lifetimes. The unspent card remains until use or replacement. Whole-card Supply adds a party allowance that persists until spent or changed by a rule. Burned Mana belongs to the current Tick's pool and ordinarily expires before the next Tick's spending.
Make motion and contact explicit. Parties have one destination, continue moving outside active columns and can receive Supply in any state. Member bodies, incoming faces, approach speed, simultaneous exchanges and retreat losses have concrete examples and replaceable geometry settings.
Implement alternatives as experiments. Board length, deployment Mana, defense aggregation, damage allocation, party health maintenance and crafting values are configuration capabilities. Temporary defaults permit complete matches without treating final balance as a prerequisite.
Support automated competition. Bots and agents are valid participants under the selected protocol. Reproducible rules simulations and two-peer automated matches exercise the same game rules, with controller identity and settings retained in reports.
Record creation and experience now. Mining, crafting, equipment changes, received definitions and creator lineage produce identified history. Final cross-match retention, learning entitlements, commerce and interruption penalties remain later policy work.
Make integration independently buildable. Local content, identity, inventory and history adapters supply complete fixture data. Existing Hapa services can replace those adapters through documented contracts; they are not undocumented prerequisites or centralized match authorities.
This revision supplies the build contract and preserves the requested experiments. Implementation reports should distinguish completed behavior, tested fixtures and scheduled capabilities, then attach actual run evidence to the exact profile and source revision used.

Starting value and meaning
Body geometry
Member body width 1; territory body width 3; contact strip width 1; center pitch 4. Member centers have offsets −1, 0 and +1 on each horizontal axis.
Party center
Global center coordinates are (4C−2, 4R−2). Board regions have width 4. At an exact region boundary retain the previous region assignment until the anchor crosses it.
Member slot orientation
Slots 1–3 are front, 4–6 middle, 7–9 rear as seen from behind the party. This fixture has four cardinal facings. Quarter-turns rotate slots and defensive faces exactly; diagonal travel preserves facing and does not rotate the grid by 45 degrees.
Ordinary Speed
Castle, Bishop, Queen, King and Commander: 1 logical step per Tick. Knight: 2. An unmounted Pawn has no ordinary party travel.
Legal destinations
Castle straight orthogonal; Bishop diagonal; Queen either; King and diagnostic Commander one adjacent square including diagonals; Knight an L endpoint. All endpoints are playable board territories.
Travel cost
1 Supply per logical orthogonal or diagonal step, including its contact strip. A complete Knight L route costs 3. Partial travel charges its actual fraction.
Knight route
Two steps on the long axis, then one on the short axis. Face along the first leg after any necessary ordinary turn. The predeclared bend adds no turn Tick and preserves that facing. Enemies along the route cause physical contact and normal engagement; no leap or automatic ride-through.
Facing change
A new orthogonal travel direction different from current facing uses one Tick and no Supply before travel. Diagonal travel preserves facing unless a separate facing order is given. Keep the old combat arrangement until completion; a Card can replace this transition.
Route replacement mid-edge
Validate a new endpoint from the known next traversal node when accepting the order. Reject an illegal replacement and retain the previous target. After accepting a replacement, finish the current edge then follow its new route. Later terrain or effect changes can block that accepted route; pause and explain those changes.
Insufficient Supply
Positive Supply permits partial travel. Pause exactly when it runs out; keep the destination. New Supply may arrive through any later agreed resource phase.
Friendly occupancy
An unrelated friendly formation obstructs travel. Do not pass through it simply because it is allied. Formation holes matter in physical contact, but ordinary party routes do not squeeze their centers through another party's territory.
Simultaneous conflicts
Propose all movement from the same starting quantum. Opponents stop at first contact and engage. Multiple allies competing for an unavailable destination or incompatible merge stop; neither player or party ID receives a hidden right of way.
Compatible merge
Before approach contact, authorize one mounted party to assemble with one friendly unmounted Pawn at an encountered route-node anchor, including an intermediate node before its final destination. Require collision-free member assembly paths and at most nine combined members. Party bounds may overlap; member-body interiors may not. Complete atomically at that anchor.
Interrupted merge
Enemy contact pauses the maneuver at the members' actual positions. The two parties retain identities until completion. Preserve per-member hit and volley markers through interruption and merge so assembly cannot grant duplicate attacks.
Slot conflict on merge
Mount remains in slot 5; preserve nonconflicting slots. Move displaced incoming retainers to empty slots in numerical order. Reject over-capacity merges. An already mounted party cannot ordinarily merge into another mounted party.
Ordinary mount death
Survivors keep their anchor and records but lose ordinary travel until a supported ability supplies a mount or movement. Commander death instead invokes the match outcome.

For the opening forward merge, use this explicit collision-free assembly pattern relative to the incoming mount's original anchor. Its center and Priest move straight forward four member widths over one Tick. Its left and right retainers first step sideways from x = −1/+1 to x = −2/+2 during the first eighth of the Tick, travel forward four widths in those strips during the middle three quarters, and step inward to their final x = −1/+1 during the last eighth. The Pawn members stay in place. Friendly boundary touching is permitted; body-interior overlap is not. These special local assembly speeds do not increase charge power. The party anchor still advances one ordinary step and spends exactly one Supply. Scale the pattern's duration for a different party Speed.
For other orientations or compositions, calculate and preview collision-free assembly paths to the agreed final slots; pause if no path exists. Validate all simultaneous assembly sweeps together. Adjacent maneuvers that need the same strip conflict and pause, rather than passing through each other. If a third party enters the assembly space, stop and resolve that interaction. At completion retain the mounted party ID, retire the old Pawn party ID, preserve every member's identity, health, equipment and hit markers, and combine remaining Supply with provenance. Preserve the mounted party's final destination and uncompleted route, then continue using any Tick time and Supply left. Later commands addressed only to the retired party ID are rejected as stale targets.
Turning and rearranging may be requested while engaged when the active-column rule allows the order. Combat continues using the old arrangement during the one-Tick transition. A legal arrangement includes each living member exactly once, keeps a living center in slot 5, preserves required support, and overlaps neither solid terrain nor another body's interior. In this fixture, an ordinary formation change cannot relocate a member out of current hostile contact. Wheel Formation changes duration only; a future Card can expressly override contact restrictions and define withdrawal consequences. Recheck legality at completion, apply a valid arrangement atomically and preserve all attack markers. On failure retain the old arrangement and emit a clear failed-completion event. Rebuild contacts without another ordinary exchange in that Tick.
Numeric precision and deterministic simulation
The first shared numeric format uses 1,000,000 integer position units per member width, 1,000,000 integer Supply units per Supply point and 1,000,000 integer health units per HP or damage point. Human-facing attack definitions report points; initialization converts them into the shared health scale. Simulate a Tick in 1,000 equal time quanta. At ordinary Speed one, a party on a straight leg advances 4,000 position units per quantum and spends 1,000 Supply units. Speed two doubles both amounts. Uphill Speed one-half halves both. Diagonal movement advances both horizontal coordinates together and still costs one Supply per diagonal step; use the larger horizontal displacement, rather than Euclidean length, for this profile's step accounting.
Speeds and modifiers are integer numerator/denominator ratios. Carry movement and Supply division remainders in the authoritative state instead of dropping them independently on each machine. Calculate each hit's power modifiers and matching protection as exact ratios, floor the nonnegative final damage to the nearest health unit, then apply it; do not carry a fractional hit into an unrelated later attack. Attack three at uphill approach Speed one-half is a 1.5-point impact before protection, representable as 1,500,000 health units. Death occurs at zero or less remaining HP.
Sweep occupied bodies over each quantum so a fast party cannot tunnel through an enemy. Clamp travel to the last non-overlapping integer position when contact occurs, charge the resulting actual distance with its carried remainder, and record that contact in the earliest quantum that reaches it. Preserve the swept contact identity even if conservative rounding leaves the visible positions one integer unit short of literal boundary equality. Attack and retreat eligibility use that recorded contact. Recompute affected sweeps when an earlier stop changes a trajectory, so later phantom contacts are not emitted. Resolve contacts with the same quantized event time together. This supplies a precise implementation grid while retaining visible intermediate positions; rendering frame rate has no authority.
The filled Queen/Knight example reaches contact after 125 quanta, one eighth of a Tick, with these dimensions. The Queen has moved half a member width. A different geometry or precision is a different saved profile, not an unnoticed numerical change. Reject values that exceed the shared safe-integer range, rather than silently overflowing. Store signed whole-number positions, nonnegative balances, ratio denominators greater than zero, and a single specified coordinate transform from gameplay height to Lumina's vertical axis.

Neither party was defending

An engagement records its initiating attacker and defender from the movement that created contact. Measure each party's positive approach component toward the other along the contact normal, using the recorded pre-stop motion. When only one approaches, that party attacks and the other defends even if the latter is moving tangentially. Thus a Queen moving west can defend against a Knight approaching her side from the north. When both approach, or neither approaches and another effect creates contact, use the mutual case. Keep these roles for that engagement's lifetime. Packet order and initiative seat do not assign them. Automatic following only enters space actually vacated and still obeys collision.
The automatic allocation fixture makes unattended tests complete. Sort legal recipient slots 1–9 and then stable member ID. In individual-protection mode, assign each whole raw hit before defense to the first recipient with positive projected HP after already assigned hits. In a shared-protection scope, assign residual health units after protection up to that recipient's projected HP, then continue with the next eligible recipient. If all recipients are projected dead but were legal in the exchange snapshot, assign the remainder as overkill to the first eligible recipient. Manual allocations may also deliberately overkill; excess damage never jumps into another protection scope.
Party-pool mode has no projected individual HP. Its automatic policy picks the first legal impact location, applies its proper protection and debits the home pool; maintenance chooses casualties. If no legal target exists in any mode, that hit produces no target damage. Record these automatic choices exactly as if a human submitted them. A human may choose any legal allocation and a bot may implement its own policy. Waiting for an explicit allocation pauses simulation at that event.
Reserve a borrowed helper's home slot while it is away. If changed terrain or an enemy nevertheless blocks return, select the nearest legal vacant home-party slot, then lowest slot number. If none exists, keep the living helper at its current legal pose with a pending return. Do not duplicate it, overlap another body, or kill it because return placement is unavailable. Its home membership and existing attack markers remain unchanged.

Appendix B Data and execution contracts
What an implementation must make explicit
This appendix turns the concepts into proposed implementation contracts. The names are new Hapa interfaces, not promises that Lumina already exposes them. An agent may organize source files differently while preserving these meanings, typed fields, deterministic behavior and acceptance results. Document schema changes and increment their version; do not make two peers infer meaning from different client code.
The complete profile in Appendix A is the semantic source for the initial configuration. Store its expanded values, not only its display name. A state fingerprint covers the rules version, expanded profile, exact content definitions, terrain, parties, resources, pending actions and all other outcome-relevant state. Events explanations and replay
Every accepted mutation produces an event with match ID, deterministic sequence, Tick/quantum or choice phase, type, participant/source identities, affected entities, before/after values where relevant, and the causal command/effect. Shared encoding identity and fingerprints
Use the proposed public_protocol_v1 encoding for application records. A signed or hashed value is JSON containing objects, arrays, strings, booleans, null and safe integers between −9,007,199,254,740,991 and +9,007,199,254,740,991. Reject decimal numeric values, negative zero, non-finite numbers, undefined values, sparse arrays, duplicate object keys and unpaired Unicode surrogates. Fractions use the declared fixed-point scale or integer numerator/denominator objects. Validate and fill schema defaults before signing; never drop invalid fields silently.
Canonical encoding recursively sorts object keys by UTF-16 code units, preserves array order and writes no insignificant whitespace. Use ECMAScript JSON string escaping without Unicode normalization, then UTF-8 without a byte-order mark. Write sorted keys directly: rebuilding a JavaScript object can reorder integer-like keys again. Both peers, bots and replay use the same encoder and frozen test vectors. This is a proposed Hapa application format, separate from Hypercore's own wire format.
The application fingerprint is SHA-256 of those canonical bytes, displayed as sha256: followed by 64 lowercase hexadecimal digits. Asset fingerprints hash the exact opaque file bytes instead. Identify the kind of digest in the manifest. As a test vector, the canonical object below has digest 43258cff783fe7036d8a43033f830adfc60ec037382473548ac742b888292777.
{"a":1,"b":2}

Use established SHA-256 and Ed25519 implementations. The documented hypercore-crypto signer operations are one supported library path. Each participant has a dedicated application signing key, whose verification key is recorded separately from its Hypercore log key and discovery key. The identity adapter binds the session signer and log to the participant. Fixture identities are labeled development identities; an integrated Hapa client resolves its supported DID binding. Hypercore continues to manage its own internal authentication and hashes. [P01, P06]
Sign the UTF-8 prefix HAPA-VERSUS MESSAGE v1 followed by a single newline, then the canonical message body. The body contains schemaVersion, type, matchId, authorId, signingKeyId, authorSequence, count, phaseId, priorStateHash and payload. The field count is the global Tick number, not the current Round. The detached Ed25519 signature is lowercase hexadecimal outside that body. Validate identity binding, signature, schema, sequence and applicable phase before passing a payload to the game rules. A valid signature does not make an illegal move legal.
Hash all authoritative state, including durations, pending choices, route progress, numerical remainders and any random stream state. Exclude sprites, camera settings, diagnostic wall-clock timestamps, derived caches and receipts/signatures that themselves refer to the state hash. Unaccepted public plan proposals are protocol inputs, not mutations of the prior gameplay state. Ready separately identifies their exact revisions and fingerprints. Match-start acknowledgments from both participants bind the complete manifest before the first mint.
Create gameplay IDs deterministically from the match ID, global Tick, phase, accepted event index and local creation ordinal. This covers minted instances, generated items and effects. Initial entity IDs derive from the manifest's stable seat, column and slot entries. Do not introduce private random UUIDs or array-order-dependent IDs into authoritative state. Keep transport-message authorSequence separate from accepted event sequence. Duplicate message delivery is a no-op after its first accepted processing; a sequence conflict is an explainable protocol error.
The base game has no random outcome in its initial fixtures. For a bot or optional operation requiring deterministic randomness, the first experiment uses the named xorshift32_v1 stream: a nonzero unsigned 32-bit state x; update with x ^= x << 13, then x ^= x >>> 17, then x ^= x << 5, reducing to unsigned 32-bit after each update. Use integer arithmetic with the specified logical right shift. Store every stream's seed and current state; a zero seed is rejected. This is a proposed reproducible experiment setting, not cryptographic randomness. A bot's private policy stream is separate from gameplay state, and all chosen bot actions are recorded. Generate signing keys through the crypto library's secure randomness, never through this stream.
Minimum developer handoff
The repository README must explain installation, the Hapa entry page, the headless fixture command, two-peer launch, profile/content locations, all four combat demonstrations, the terrain/crafting fixture, and replay export/verification. Supply the exact commands implemented by that revision rather than copying aspirational names from this document. Link each acceptance scenario to its fixture and expected results.
An implementation report identifies the source revision, runtime, supported platforms actually tested, profile and content fingerprints, completed scenarios, known placeholders and remaining failures. A screenshot proves what was displayed; replay equality proves agreement; neither alone proves the whole game is correct. Keep these evidence types distinct. The requirements are ready for an agent to begin development when it can trace every core rule to a field, operation, visible result and verification scenario described here.
